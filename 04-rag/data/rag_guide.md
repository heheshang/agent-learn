# RAG 检索增强生成

检索增强生成（Retrieval-Augmented Generation，RAG）是一种把外部知识库接进大语言模型的方法。
它的核心思路是：模型回答之前先去检索相关文档片段，把这些片段作为上下文塞进提示词。

## 为什么需要 RAG

大语言模型存在几个根本限制。首先是知识截止日期，模型的训练数据有截止时间，之后发生的事情它一无所知。
其次是幻觉问题，模型在不知道答案的时候会编造一个看起来合理的答案。
第三是知识无法更新，重新训练模型代价高昂，而 RAG 只需要更新向量库。

第四是数据隐私，企业内部文档不能拿去训练公开模型。
第五是可溯源，RAG 的每个答案都能追溯到具体的文档片段，这一点在合规场景里至关重要。

## 基本架构

一个典型的 RAG 系统由两个阶段组成。

### 索引阶段（离线）

索引阶段负责把原始文档变成可检索的结构。流程是加载文档、分割成块、计算嵌入向量、存入向量库。

```
原始文档 → Loader → 文本块 → Embedder → 向量 → Vector Store
```

### 查询阶段（在线）

查询阶段处理用户的提问。流程是问题编码、在向量库检索、拼装提示词、调用模型。

```
用户问题 → Embedder → 相似度检索 → Top-K 文档块 → 拼装 Prompt → LLM → 答案
```

## 文档加载

文档加载是流水线的第一步。不同格式需要不同的工具。

Markdown 文件可以直接读取，但要注意保留标题层级，因为标题提供了天然的语义边界。
HTML 需要剥掉标签，PDF 是最难处理的：可能是扫描件（需要 OCR）、可能有复杂的多栏排版、
表格的结构在纯文本抽取后会丢失。

Docling 这类结构感知解析器会先把文档转成带层级的中间表示，再做分块，
比纯文本抽取保留了更多结构信息。

## 文本分块策略

分块是 RAG 里最影响效果、也最被低估的一步。

块太大，检索精度下降，一个块里混了多个主题，向量语义被稀释。
块太小，语义不完整，模型拿到碎片后无法理解上下文。

### 固定大小分块

最简单的策略，按固定字符数或 token 数切分。实现简单，但会在句子中间切断。

### 递归分块

按优先级递归尝试分割点：先按段落，再按句子，再按词。
这是 LlamaIndex SentenceSplitter 和 LangChain RecursiveCharacterTextSplitter 的核心思路。

### 语义分块

用嵌入模型比较相邻句子的相似度，在相似度骤降的位置切开。
理论上最优，但成本高，需要每句都算一次嵌入。

### 文档结构感知分块

利用文档自身的结构边界：标题、章节、表格。
对 Markdown 和结构化 PDF 效果最好，因为边界是文档作者明确标出的。

## 重叠

相邻块之间保留一部分重叠内容，避免关键信息正好落在切分线上。

重叠太小，关键句被切断。重叠太大，存储和计算成本翻倍，还会引入重复内容干扰检索。
经验值是块大小的 10% 到 20%。

## 元数据

每个块都应该带上元数据：来源文件、标题路径、页码、块序号。
元数据在检索后用来过滤和引用，比如「只在这个章节里检索」或者「引用时标注页码」。

标题路径尤其重要。把 `# 文档标题 > ## 章节 > ### 小节` 作为前缀附加到块文本上，
能让嵌入向量带上层级语境，检索命中率明显提升。

## 常见陷阱

第一，块大小用字符数估算 token 数。这在中文和代码里误差很大，应该用真实的 tokenizer。

第二，忘记给块加标题路径。语义相同的句子在不同章节里含义完全不同。

第三，表格被拍平成一行文本。表格的结构信息丢失后，检索基本无效。

第四，只做召回不做重排。向量检索召回 20 条，再用交叉编码器重排取 top 3，效果提升明显。

第五，测试集泄漏。用测试问题评估时，如果文档内容本身包含了答案，指标会虚高。

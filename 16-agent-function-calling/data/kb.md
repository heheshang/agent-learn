# Function Calling 知识库

本文件是 `16-agent-function-calling` 的 `search_knowledge` 工具背后的知识库。
Agent 通过这个工具从这里召回片段 —— 就像 LangChain 官方示例里的
`Wikipedia` 工具一样，只是把「维基百科」换成了「本地知识库」。

## Function Calling 是什么

Function Calling（也称 tool calling）是让模型与外部系统交互的一种机制。
开发者把一组「工具」（函数）的定义放进 API 请求，模型在生成回复时
可以决定「我需要调用某个工具」，并给出结构化的调用参数。

它要解决的问题很具体：模型**只见过训练数据**。
问它「现在北京天气怎么样」，它要么不知道，要么编一个。
Function Calling 让模型能说「我不知道，但我可以查」。

三个核心概念：

- **Tools** —— 交给模型的功能（查天气、查订单、发退款）
- **Tool calls** —— 模型发出的调用请求（带工具名和参数）
- **Tool call outputs** —— 你的代码执行工具后返回给模型的结果

## 五步调用流程

Function Calling 是一个多轮对话，而不是一次请求：

1. 带上工具定义发起请求
2. 收到模型的工具调用
3. 在应用侧执行代码
4. 带上工具输出再次请求
5. 收到最终回复（或者更多的工具调用）

关键在于第 4 步：你要把**所有**东西一起发回去 ——
工具定义、原始提问、模型的工具调用、以及工具的输出。

## 工具定义长什么样

每个可调用函数都有同一套 Schema 形状：

| 字段 | 说明 |
|---|---|
| `type` | 固定是 `function` |
| `name` | 函数名，例如 `get_weather` |
| `description` | 何时以及如何使用这个函数 |
| `parameters` | 定义输入参数的 JSON Schema |
| `strict` | 是否强制严格遵守 Schema |

`parameters` 是标准的 JSON Schema，所以可以���用它的丰富特性：
属性类型、枚举、说明、嵌套对象、递归对象。

## strict 模式

把 `strict` 设为 `true`，能确保函数调用可靠地遵守 Schema，
而不是尽力而为。官方建议始终开启。

它的底层是 structured outputs，因此有两个硬要求：

1. `parameters` 里每个对象的 `additionalProperties` 必须设为 `false`
2. `properties` 里所有字段都必须标记为 `required`

可选字段的正确写法是把 `null` 加进类型数组，例如 `"type": ["string", "null"]`。

如果 Schema 不满足要求，请求会被拒绝并告诉你缺了哪些约束。

⚠️ **注意**：strict 模式只对部分模型和部分 API 有效。
其它厂商可能接受这个字段但**不执行**它 —— 所以本地校验依然必要。

## 工具选择：tool_choice

默认情况下模型自己决定何时调用、调几个。你可以强制指定：

- `auto` —— 默认，模型自己决定
- `none` —— 一个都不调
- `required` —— 至少调一个
- 指定函数 —— 必须调那一个

`none` 特别有用：它让你能对照出「模型自己决定用工具」到底值多少。

## 并行函数调用

模型可能在**一轮里**返回多个工具调用。
只要这些调用之间没有依赖关系，并行执行能显著降低延迟。

要禁止并行，把 `parallel_tool_calls` 设为 `false`。

⚠️ 注意：部分厂商（包括 DeepSeek）**接受但不执行**这个参数 ——
实测传了 `parallel_tool_calls: false`，模型照样一次返回多个调用。
并行度只能靠应用层自己控制。

## 工具调用的错误处理

工具执行失败时，**不要**把整个请求返回错误。
正确的做法是把错误信息作为工具输出回传给模型，让它自己纠正。

```text
assistant: tool_calls=[get_weather(city="Atlantis")]
tool:      错误：找不到城市 `Atlantis`，请换一个城市名。
```

模型读到这条信息后通常会换一个参数重试，或者向用户澄清。

同样的道理适用于参数校验：参数填错时**不要发请求**，
先在本地校验，并把「哪个参数、期望什么、实际是什么」告诉模型。

## 定义函数的最佳实践

1. **写清楚函数名、参数说明和使用说明**
   - 明确描述函数的目的、每个参数的格式，以及输出代表什么
   - 在 system 提示词里说明何时（以及何时**不**）该用这个函数
   - 给出示例和边界情况，尤其是为了纠正反复出现的失败
2. **遵循软件工程最佳实践**
   - 让函数可预测、直观（最小意外原则）
   - 用枚举和对象结构防止无效状态
   - 通过「实习生测试」：只看你给模型的信息，一个新人能用对吗？
3. **把负担从模型身上卸下来**
   - 不要让模型填你已经知道的参数
   - 总是成对出现的函数，合并成一个
4. **保持初始可用函数数量足够少**
   - 建议一开始少于 20 个函数 —— 太多会让模型过载并增加错误
5. **善用平台资源**
   - 在 Playground 里生成和迭代 Schema
   - 工具多或任务难时，考虑微调提升 function calling 准确率

## 工具调用与 token 消耗

函数定义在底层被注入到 system 消息里，以模型训练过的语法表达。
这意味着**可调用函数的定义会计入上下文限制，并按输入 token 计费**。

如果撞上 token 限制，可以：减少初始加载的函数数量、缩短描述、
或者用 tool search 把不常用的工具延迟加载。

## 提示词与工具的关系

GPT Best Practices 建议的提示词结构是：

- **Identity** —— 助手的角色与目标
- **Instructions** —— 行为规则（包括何时调用函数）
- **Examples** —— 示例输入与期望输出
- **Context** —— 其它补充信息

其中一条是「**用 system 提示词描述何时（以及何时不）使用每个函数**」。
另一条是「**不要让模型填你已经知道的参数**」。

最后一条对 function calling 尤其重要 ——
工具的参数应该只包含**模型需要决定**的东西。

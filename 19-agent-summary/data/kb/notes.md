# 项目笔记

## 架构

本项目是 agent-learn workspace 的第 19 个成员，也是**第一个把前面所有项目串起来**的项目。

整体链路：HTTP 层 → Agent 循环 → 工具层 → 证据层 → 报告层。

### 三阶段流水线

研究阶段（Agent 循环，多轮工具调用）产出证据集合，成文阶段（一次纯文本调用，不带工具）产出结构化 JSON，校验阶段（纯代码）产出接地状态。

### 为什么分成三个阶段

如果在一个提示词里同时要求「查资料」和「写报告」，模型会倾向于先写——写作的 token 收益更高——然后顺手编几个引用编号。分成两阶段后，写报告时的输入只有证据，模型想编也编不出细节。

## 错误处理

### 三个类别

工具失败必须声明类别：Transient（上游临时故障，可重试）、Business（调用方参数错，改参数才行）、Fatal（环境没配好，重试和降级都徒劳）。

类别决定处置策略，不是靠错误文案。文案会变，分类决策必须稳定。

### 降级策略

Transient 重试（指数退避），Business 降级成观察喂回模型让它自我纠正，Fatal 终止。

致命错误终止后不返回模型的答案——模型可能在上一步说了些话，但那不是基于工具结果的答案。

### 每个 tool_call 恰好一条回执

少一条回执，整个请求 400。而且致命错误也要生成回执，否则下一轮请求会 400。

## 工具

### 五个工具

本地知识库检索（BM25 倒排索引）、Web 搜索、网页正文抓取、长期记忆读写、手写算术求值器。

OpenAI 最佳实践建议初始可用函数少于 20 个。工具越多，模型的选择空间越大。

### 工具优先级

先查本地知识库（零延迟、结果稳定），再查长期记忆，最后才搜互联网（有时效性但可能失败）。

### 参数错了别发请求

Schema 本地校验，错误信息必须可执行——指出哪个参数、期望什么、实际是什么。

## 检索

### BM25 是关键词检索

BM25 不理解语义。中文分词是 unigram 加 bigram，所以「量子计算」里的「算」会命中「算法」。这不是 bug，是中文关键词检索的固有特性，要解决得靠重排或向量检索。

### 用块正文不用标题

BM25 检索用块正文，标题信息通过 heading_path 字段单独保留。如果把标题也塞进正文，标题词会主导打分。

## 记忆

### 事实的三段结构

主语、谓语、值。去重键是 owner 加 subject 加 predicate，不是整条内容——「用户叫 Bob」和「用户名字是 Bob」应该被认成同一件事。

### 只增不覆盖

旧值进 versions，新值成为当前值。用户改口时旧信息不是没用。

### BM25 索引是可重建的

索引是缓存，文件才是真相来源。索引丢了重建，不影响记忆本身。

## 报告

### 接地三态

Grounded（每条结论都引用了真实存在的证据）、PartiallyGrounded（部分结论引用了不存在的证据）、Ungrounded（一条证据都没引用）。

### 悬空引用优先

只引用了伪造编号（E99）也判 PartiallyGrounded，不能判 Ungrounded。「没引用」是诚实，「引用了不存在的」是幻觉，两者混在一起会掩盖幻觉。

### 默认值是 Ungrounded

「默认接地」是最危险的默认值——模型没引用任何东西时，如果默认是 Grounded，校验就形同虚设。

## Web 搜索

### 搜索要抽象成后端

搜索服务的可用性因网络环境而异。在受限网络里，通用网页搜索只有 Bing 可靠，而技术类搜索有 GitHub API 更稳。

### HTML 提取的三个坑

HTML 不是文本，脚本和样式要整块删除。行内标签剥掉后两侧要补空格，否则「第一个第二个」会粘成一个词组。HTML 实体不解码的话模型会看到一堆 &amp;。

### 抓取只允许 http 和 https

挡掉 file:// 和 data: 这类本地读取。
